# Direct composition consumers and version selection

This approved migration supersedes the simulation-only boundary in
COMPOSITION_MIGRATION.md and the software migration's first-version projection.

Products, devices and software editions own BOM composition in composition_history.
The two November 29, 1982 professional-video/monitor assemblies are now device
version 2. Their version 1 intervals end on that day, exclusively. Technical
revision notes refer to composition_version_number. All 26 empty product wrappers
are removed; assemblies.json is empty. The two historical revision records join
retired_assemblies.json, which is never loaded by current page projections.

composition-resolver.js is the one traversal implementation. The browser imports
it directly; tools/compositions.py calls it through tools/resolve_compositions.cjs.
A root requires an explicit version or date. For each child, select
child.valid_from <= parent.valid_from < child.valid_to, and repeat at the selected
child's own valid_from. Missing/overlapping coverage is an error, not a fallback.
Physical leaves preserve quantity, unit, conditions and path. Repeated supplies on
different paths remain separate; unknown quantities propagate rather than becoming
one. Nonmaterial services are visible in commercial composition but do not become
manufacturing materials. Products remain flat; devices/software may be nested.

Both the BOM Navigator and computer-page Bill of materials panels provide a
Composition version selector labelled YYYY-MM-DD - YYYY-MM-DD. It defaults to the
latest recorded version. On computer pages, changing the root version also updates
the displayed configured hardware. Inspecting an included device initially selects
its version from the selected product tree. A device viewed independently can select
any of its own versions. The computer selector still qualifies solely by computer_line.

Saved cost evaluations retain their own dates; they do not mutate the chosen BOM.
Cost builders select compositions at their explicit evaluation date. November
build calls pass 1982-11-29, not the annual June snapshot. Root and child selection
remain distinct. Routing requires qualified metadata on the selected owner/version,
not assembly-ID string heuristics. Unknown quantities/conditions/costs block exact
costing. Existing rebuild qualification guards remain in force. No financial model
or frozen baseline is rebuilt by this migration. The physical material-cost helper
is explicitly materials-only and does not claim complete manufacturing cost.

Compatibility boundary: catalog:hardware-bom remains a deprecated read/export
shape for historical audit tests and existing one-version import tooling. It is
constructed in memory from composition owners, never from active/retired assembly
records. Current BOM pages, computer configurators, supplementary site details,
source integrity validators and cost traversal do not consume its assembly graph.
This boundary is not another persisted catalogue. Registry composition_aliases
maps former assembly IDs to owner AND version; old device-revision links retain
that distinction. Saved numerical archive IDs/values are unchanged.

Verification compares all 72 product versions against pre-cutover source
inventories, independently of the 27 former financial-BOM comparisons. Sixty-four
are unchanged. Four November products gain two AION 2114 chips each, as documented
in COMPOSITION_SIMULATION.md. All 164 owner versions resolve. Thirty-seven distinct
physical parts have unknown quantities across all owner versions, broader coverage
than the earlier product-only simulation. Existing unresolved quotation scopes and
multi-host qualification constraints are unchanged.

Run tools/validate_data.py, tests/validate_data_structure.py,
tests/validate_composition_cutover.py, tests/composition-resolver.test.cjs and
tests/composition-version-ui.test.cjs, plus the product/device/software suites.
Old migration fixtures are preserved; composition-cutover.json records the reviewed
compatibility export delta, while composition-product-inventories.json records
pre-cutover physical inventories for every product version. Neither fixture is a
financial baseline. COMPOSITION_SIMULATION.md is regenerated by the read-only audit.

Final regression found Abacus 3 inclusion on both Budget products was declared only
in software_variants. That existing promise now lives in their composition histories:
the floppy Budget product gains a 1980-11-19 intermediate version; both products'
subsequent versions include the edition. The redundant software_variants fields are
removed. This adds physical delivery lines to four Budget versions, in addition to
the four video-revision inventory changes. The earlier software overlay is not lost.
